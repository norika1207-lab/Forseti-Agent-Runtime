## 0　這套系統在解決什麼

### 0.1　問題不是 AI 會出錯，是它出錯的時候沒有訊號

一般的錯誤會報錯、會失敗、會有紅字。這套系統要處理的是另一種：

```
AI 說「改好了」          → 磁碟上沒動靜
AI 說「我讀完了」        → 實際只讀了三成
AI 說「還沒做完」        → 然後停下來等人說繼續
AI 被壓縮之後            → 說自己記得，追問深度才承認只取樣
worker 死了              → 十七小時沒有人知道
```

這五種都不會報錯。系統看起來一切正常，人也感覺不到，直到很久之後
才發現方向早就歪了。

### 0.2　北極星

> 讓 AI 的工作狀態變成可觀測、可驗證、可控制、可復原。
> 使用者不該變成 AI 的保姆、QA 部門、或手動復原機制。

出自 `.forseti/NORTH_STAR.md`。

三句不變量：

```
AI 可以死，但 Project State 不能死。
AI 可以換，但 Reality 不能換。
Session 可以 Fork，但 Goal、Decision、Evidence 與 Verified State 必須完整延續。
```

### 0.3　一個實測數字說明問題有多大

`HumanContinueBurden` 定義在 F06 §5：每個任務裡人類必須說「繼續」的次數，
應趨近於零。

2026-09-09 這一場實測 **9 次**。

也就是使用者被當成心跳器用了九次。每一次的形狀都一樣：AI 做完一件事、
寫一份完整的報告、停下來，等人說繼續。而每一份報告單獨看都是好的。

## 1　系統架構

### 1.1　五層

```
                        人
                        ↕
        ┌───────────────────────────────┐
        │  Main Session（認知控制平面）    │  詮釋、架構、優先序、驗收
        └───────────────────────────────┘
                        ↕
        ┌───────────────────────────────┐
        │  Forseti 控制與可靠性平面        │  任務真相、派工、事件、證據
        └───────────────────────────────┘
                        ↕
   ┌────────────────────────────────────────────┐
   │  Task Ledger │ Event Bus │ Evidence │       │
   │  Watchdog    │ Context Store                │
   └────────────────────────────────────────────┘
                        ↕
        ┌───────────────────────────────┐
        │  Sub-session / Worker（執行平面）│  code、build、test、批次
        └───────────────────────────────┘
                        ↕
             工具 / 程式碼 / 外部系統
```

分工用一句話講：Main 擁有詮釋與驗收，Worker 擁有執行，
Forseti 擁有持久的任務真相與連續性。

### 1.2　核心不變量：Turn completion is not Task completion

```
對話生命週期   ≠  執行生命週期
Session 記憶   ≠  任務真相
模型自述       ≠  已驗證完成
心跳           ≠  進度
```

這四條是整套設計的地基。每一條都對應一個實際發生過的事故。

### 1.3　三條並行的線

| 線 | 處理什麼 | 狀態 |
|---|---|---|
| 主線（階段 0-5） | AI 有沒有偏離目標、有沒有唬爛 | 階段 0 `VERIFIED`，1-5 未開始 |
| C 線（C0-C5） | AI 被壓縮之後怎麼繼續正常運作 | C0、C1 `DONE`，C2 已由 F08 取代 |
| F 線（F01-F08） | 執行的連續性與可靠性 | 八個 feature 全部 `VERIFIED_COMPLETE` |

它們處理三種不同的失效，所以分開走。合併會出現一個荒謬：
用一個已經忘記北極星的 AI，去偵測自己有沒有偏離北極星。

## 3　運作方式

### 3.1　一個任務的完整生命週期

```
  owner 說「做這件事」
        ↓
  accept()  ─── 義務從這一刻起活在模型外面
        ↓
  transition(RUNNING)  ─── 每次轉換都必須有事件因
        ↓
  ┌──→ auto_dispatch()  ─── 四條件滿足就自己走
  │         ↓
  │     dispatch(step, worker)
  │         ↓
  │     worker 做事，過程中發 WORKER_PROGRESS
  │         ↓
  │     receipt()  ─── 結果在合成之前先落地
  │         ↓
  │     submit_result(packet)  ─── 只到 VERIFYING，不是完成
  │         ↓
  │     verify_step()  ─── 真的去看磁碟
  │         ↓
  │     過 → VERIFIED_COMPLETE      沒過 → 回 RUNNING，retry_count +1
  │         ↓
  └─────────┘  下一步
        ↓
  全部完成 → 任務進 VERIFYING → owner 驗 definition_of_done
```

### 3.2　狀態機

```
PROPOSED ──→ ACCEPTED ──→ RUNNING ←──────────────┐
                 │            ↕                    │
                 │      WAITING_DEPENDENCY         │
                 │            ↕                    │
                 │        BLOCKED                  │
                 │            ↕                    │
                 │      NEEDS_HUMAN                │
                 │            ↕                    │
                 └──────→ VERIFYING ───────────────┘
                              │
                              ↓
                    VERIFIED_COMPLETE

任何狀態都可以 → CANCELLED_BY_OWNER | SUPERSEDED（擁有者的權力）
RUNNING/BLOCKED/… → FAILED_TERMINAL
```

十一種狀態，四種終止。

**`VERIFYING` 可以回到 `RUNNING`** —— 驗證沒過要回去做，不是直接失敗。

### 3.3　為什麼 verifier 只支援兩種形式

```
file:<path>    檔案存在且非空
cmd:<command>  指令 exit code 0
```

刻意不支援 `manual:` 或 `asserted:` 這種由人或模型宣告通過的形式。
那種東西就是 claim，而不信 claim 正是這個專案存在的理由。

如果 verifier 可以用嘴巴過，CT-F02-01「宣稱 done 但缺收據要維持非終止」
這條測試就是假的，而假的驗證比沒有驗證更危險。

## 4　每個參數代表什麼

### 4.1　`worker.py` 污染預算

| 參數 | 值 | 意思 | 依據 |
|---|---|---|---|
| `SUMMARY_LIMIT` | 2000 | worker 回報摘要的字元上限，超過拒收 | **拍的，無實測** |
| `LIST_LIMIT` | 40 | artifacts/evidence 等清單的長度上限 | **拍的** |
| `RAW_INLINE_LIMIT` | 4000 | 超過就一律落檔，不進 packet | **拍的** |
| `WORKER_STATUS` | 4 種 | COMPLETED / BLOCKED / FAILED / PARTIAL | 規格 F03 §4 |

**為什麼是拒收不是截斷**：一個被截斷但看起來正常的 packet，比一個被拒絕的
packet 危險，因為前者會讓 Main 以為自己看到了全部。

### 4.2　`watchdog.py` 停滯偵測

| 參數 | 值 | 意思 |
|---|---|---|
| `min_age_sec` | 300 | 低於這個秒數一律不判定停滯 |
| `saturate_sec` | 3600 | 到這個秒數 duration 因子飽和到 1.0 |
| `suspect_at` | 0.5 | STALL_RISK 超過就標 `STALL_SUSPECT` |
| `unresponsive_limit` | 3 | 連續無回應幾次就跳到重派 |

`STALL_RISK` 是四個因子相乘，每個 0 到 1：

```
STALL_RISK = duration_anomaly
           × no_progress_growth
           × no_event_activity
           × expected_progress_confidence
```

**相乘的意思是任何一個因子接近 0 就足以洗掉懷疑。** 這正是規格說的
「長時間本身不足以判定」的機制形式。

最後一個因子是關鍵煞車：如果這一步本來就不預期有可見產物（例如在等
外部依賴），再久也不算停滯。沒有它，所有等待都會被誤判成卡住。

**這四個門檻全部沒有實測校準。** 規格只給了公式沒給值域，
`watchdog.py` 檔頭標明那是我的詮釋不是規格原意。

### 4.3　`rehydration.py` Context Coverage

七級量表，出自規格 F08 §5 與平台 Vol2 §4：

| Level | 意思 |
|---|---|
| 0 `NONE` | 完全未讀 |
| 1 `TITLE_ONLY` | 只見檔名或標題 |
| 2 `HEADER_SCAN` | 讀檔頭或摘要 |
| 3 `SAMPLED` | 取樣讀了部分段落 |
| 4 `STRUCTURAL` | 讀完整結構與關鍵段落 |
| 5 `FULL_READ` | 逐段完整讀取 |
| 6 `VERIFIED_UNDERSTANDING` | 完整讀取後能正確引用、重建、通過 challenge |

**5 跟 6 的差別是整張表最重要的一條**：5 是我說我讀完了，6 是有人考過我。

`coverage_of()` 從實際讀過的範圍算，不從宣稱算。沒有 `read_ranges`
就是 `NONE`，不管誰說他讀過。

| 參數 | 值 | 意思 |
|---|---|---|
| `PACKET_LIMIT` | 8000 | RehydrationPacket 的字元上限 | 

**這個數字也是拍的。** 合理的值應該從「Main 讀完之後還剩多少判斷力」
量出來，而那還沒有辦法量。

### 4.4　`starvation.py` 空輸出

| 參數 | 值 | 意思 |
|---|---|---|
| `BLANK_SEQUENCE_AT` | 2 | 連續幾次空輸出算 sequence | 
| `OBSERVED` / `INFERRED` | — | 每個診斷的依據標記 |

`OBSERVED` 與 `INFERRED` 這一對是規格 F07 §3 的界線做進資料結構：
Forseti 無法直接證明隱藏推理被吞掉，所以根因必須分開觀測與推論。

**寫在註解裡的界線會被忽略，寫在欄位裡的不會。**

### 4.5　`continuity.py` 停止理由

八種合法的停止理由：

```
WAITING_EXTERNAL       在等外部系統，等的對象要講得出來
BLOCKED_VERIFIED       真的被擋住，而且擋住的事實驗證過
NEEDS_HUMAN_DECISION   需要擁有者做一個只有他能做的決定
RETRY_BACKOFF          退避中，會自己回來
RESOURCE_LIMIT         資源上限
POLICY_BOUNDARY        政策或安全邊界
WORKER_FAILURE         worker 失敗
UNKNOWN_STOP           不知道為什麼停了
```

前三種必須講得出對象，不然跟「我先停一下」沒有差別。

`UNKNOWN_STOP` 刻意保留為合法：不知道為什麼停了是誠實的答案，
比硬掰一個好。它是告警不是正常出口，但誠實的告警勝過漂亮的謊。

**明文無效的理由**（規格 F06 §4 直接列的，不是我加嚴）：

```
「turn ended」      對話的一輪結束不等於任務結束
「I explained it」  解釋不是交付
「等你說繼續」      下一步已授權的話就該自己走
「做完了」          完成要靠 verifier 判定
```

## 5　事件定義

### 5.1　事件是什麼，為什麼需要它

規格 F02 §5：**每一次狀態轉換都必須有事件因。**

自然語言的陳述不會改變確定性狀態，除非它被解析成一個核准的狀態事件。
所以 `transition()` 沒給 `cause` 會直接丟例外，跟「狀態不合法」同一類錯誤。

### 5.2　八種 worker 事件（規格 F04 §3）

| 事件 | 意思 |
|---|---|
| `WORKER_ACCEPTED` | worker 接下這一步 |
| `WORKER_PROGRESS` | 有進度。**只證明它還會說話，不證明有東西被做出來** |
| `WORKER_COMPLETION` | 宣稱完成。只讓步驟進 `VERIFYING` |
| `WORKER_BLOCKED` | 被擋住，必須說出被什麼擋住 |
| `WORKER_FAILED` | 失敗，`retry_count` +1 |
| `WORKER_CANCELLED` | 被取消 |
| `EVIDENCE_AVAILABLE` | 有證據可查 |
| `ARTIFACT_CHANGED` | 產物變動 |

**只收這八種。** 事件種類可以隨便取名等於沒有協定，
下游沒辦法對著一組不固定的名字寫邏輯。

### 5.3　控制端自己的事件

實測帳本裡目前 65 筆事件，12 種：

| 事件 | 筆數 | 意思 |
|---|---|---|
| `STEP_STATE` | 29 | 步驟狀態轉換 |
| `DISPATCH` | 8 | 派工 |
| `WORKER_RESULT` | 7 | 收到 worker 的 packet |
| `TASK_STATE` | 6 | 任務狀態轉換 |
| `RECOVERY_RUNG` | 3 | 復原階梯往下一階 |
| `PROGRESS_PROBE` | 3 | watchdog 取樣產物 |
| `WORKER_FAILED` | 2 | worker 失敗 |
| `TASK_ACCEPTED` | 2 | 接受任務 |
| `REASSIGN` | 2 | 換 worker |
| `WORKER_ACCEPTED` | 1 | worker 接下 |
| `STALL_SUSPECT` | 1 | 疑似停滯 |
| `HUMAN_CONTINUE` | 1 | **人被迫說「繼續」** |

最後一個是負向指標。每記一筆，就是系統失敗了一次。

### 5.4　冪等

規格 F04 §4：事件必須是 durable 而且 idempotent，
重複的完成事件不得執行下一步兩次。

實作是資料庫的 unique index 在 `idem_key` 上，
**不靠呼叫端記得檢查 —— 呼叫端會忘記，索引不會。**

沒給 `idem_key` 的事件不去重，因為預設去重會把兩次真實的進度回報吃掉一次。

## 6　實務情境（十四個）

### 情境一：AI 說改好了，但磁碟沒動

```
AI:  「我把 config.py 的逾時改成 30 秒了」
```

`verify_step()` 跑 `file:config.py` 加上比對 mtime，發現檔案沒動過。
步驟從 `VERIFYING` 退回 `RUNNING`，`retry_count` +1。

**任務不會終止**，因為 F01 §3 規定終止狀態只有四個，
而「AI 說做完了」不在其中。

### 情境二：AI 報告完就停下來等人

```
AI:  「前兩步做完了，摘要如下……」（然後停住）
```

`report()` 這個函式**沒有任何可以順手改狀態的參數**，是刻意的。
報告記成 `PROGRESS_REPORT` 事件，任務維持 `RUNNING`。

`next_step()` 立刻回傳第三步，`auto_dispatch()` 直接派下去。

人不需要說任何話。

### 情境三：人還是說了「繼續」

呼叫 `human_continue()` 記一筆。這個函式存在的唯一目的是讓
`HumanContinueBurden` 算得出來。

```
burden = 0      沒有人需要說繼續
burden ≤ 2      還在可接受範圍
burden > 2      使用者被當成心跳器用了
```

2026-09-09 這一場整場 9 次，任務期間 1 次。

### 情境四：worker 交回 100KB 的編譯 log

```
worker: [100,000 字元的 compiler output]
```

`stash()` 把它落檔，回傳 `path#100000chars`。
packet 只帶那個引用，實測 packet 本身小於 2,000 字元，是原始輸出的 1/50。

Main 拿到路徑，要不要讀是它的選擇。**塞進 packet 的話 Main 沒有選擇，
它一定會進 context。**

### 情境五：worker 順手多做了幾件事

```
worker: artifacts = ["out.txt", "順手改的 config.yaml", "新開的 extra.py"]
```

`check_scope()` 比對 `TaskStep.expected_outputs`，
標出兩個範圍外的產物，packet 被拒收。

判準是結構的：產物在不在清單裡。**偏離不會公告**，worker 會安靜地
多做幾件事一起交回來，而那些多出來的東西看起來都很合理。

### 情境六：TaskStep 沒定義預期產物

`check_scope()` 回空清單，不判定超出範圍。

**沒有範圍就談不上超出範圍。** 那是 TaskStep 沒定義好，不是 worker 的錯，
混為一談會開始責怪 worker 做對的事。

### 情境七：長時間建置

```
worker 跑了兩小時，build.log 一直在長
```

`check_liveness()` 取樣 `expected_outputs` 的 hash，發現有變動，
`no_progress_growth` = 0，整個 `STALL_RISK` 乘成 0。

判定 `ALIVE`，理由「產物有變動，正在做事」。

**把「久」當成「卡住」會讓所有長工作都被誤判，而長工作正是最不該
被打斷的那種。**

### 情境八：worker 真的卡住了

跑了兩小時，產物沒動，也沒有任何事件。四個因子都接近 1，
`STALL_RISK` = 0.996，判 `STALL_SUSPECT`。

復原階梯往下走，人排在最後：

```
SUSPECT → SOFT_PING → INSPECT_STATE → STRUCTURED_STATUS
→ CHECKPOINT → RESTART_OR_REASSIGN → CLEAN_FORK → HUMAN
```

**叫人是最貴的一步，不是最方便的一步。**

### 情境九：worker 活著但做錯了

心跳正常、產物一直在動，但產物是空檔案。

`check_liveness()` 回 `ALIVE`（它只回答活不活著），
`verify_step()` 回不通過，產生 `CORRECTNESS` incident。

**兩條線分開的理由不是分類整齊，是混在一起會出現最糟的情況：
心跳正常於是沒人去看產物，而產物是錯的。**

### 情境十：建置成功但最終輸出是空白

工具跑完了，`ResultReceipt` 已經落地，但那句話沒送出去。

`diagnose_output()` 判 `OUTPUT_STARVATION`（basis: `OBSERVED`），
`recoverable_without_rerun` = true。

恢復計畫是 `PRESERVE_RESULTS → MARK_AVAILABILITY → SYNTHESIS_ONLY
→ AVOID_RERUN`。

**已經花掉的建置時間是真的成本，不該因為一句話沒說出來就再付一次。**

### 情境十一：連續空白

`blank_run` ≥ 2 判 `BLANK_OUTPUT_SEQUENCE`，恢復計畫多一步
`CLEAN_RESPONSE_WORKER`。

單次可能是意外，連續不是。**重複本身就是證據。**

### 情境十二：壓縮發生了

`forseti context` 讀 jsonl 的 `compact_boundary` 事件，拿到精確的帳：

```
18:56:45  auto  997,325 → 17,472  丟棄 979,853  歷時 2m58s
```

`CompressionBoundary.task_state_intact` 比對壓縮前後的任務狀態。
**會變的話代表任務真相跟著 context 走，那整個帳本就白做了。**

然後 `challenge()` 問四個具體問題，不是問「你還記得嗎」——
那個問題的答案永遠是「記得」，2026-09-09 這一場實際發生過。

### 情境十三：新 session 接手

```
$ forseti doctor
```

從控制檔讀出北極星、當前階段、哪幾份沒讀完、有哪些阻塞、未完成幾項。

2026-09-09 實測：一個全新 session 只拿到一句「接手這個專案，
告訴我現在該做什麼，還有哪些事沒做完」，沒有人告訴它有這個指令，
它自己找到了，並且四件事全部答出來。

### 情境十四：要找回被壓縮丟掉的東西

```
$ forseti recall "為何會有點名板"
```

從 73,115 段索引裡撈，被壓縮丟出 context 的段落加權，
糾正過的位置標出來，過時的講法標「之後有人糾正過同一批檔案」。

輸出是一句話加一個地址，不是一坨資料。要細節自己去讀那一段。

## 11　把 F04 接上去（2026-09-09 當天完成）

§8.2 第一項寫的是「做出一個能自動繼續的東西，跟真的讓它自動繼續，
是兩件事」。這一節記錄它怎麼被解掉，以及過程中撞到的兩個東西。
過程比結論有用，因為結論只有一行，過程裡有兩個沒有人會發現的錯。

### 11.1　根因不是我懶得用它

原本的診斷是「我做完 `auto_dispatch()` 之後自己走手動」。動手第一件事
是盤 CLI，結果是：

```
doctor  status  gate  context  index  recall  tasks
```

七個命令，沒有一個碰得到 F03 到 F06。`dispatch`、`auto`、`drain`、
`event`、`verify`、`continuity` 全部只存在於 Python API 裡。

也就是說，除了單元測試以外，**沒有任何東西呼叫得到 `auto_dispatch()`**。
不是我不用它，是沒有門可以進去。一個沒有入口的機制等於不存在。

修法是補上那六個 CLI 入口。其中 `auto` 特別處理了一件事：
`auto_dispatch()` 回 `None` 有三種意思（任務已終止、沒有下一步、
需要人決定），CLI 必須把三種分開講。安靜的 `None` 正是這整套東西
要消滅的東西 —— 使用者不該從「沒反應」去推發生了什麼事。

### 11.2　第一個錯：指標在用字串猜自己有沒有被用

`continuity()` 判斷一次派工是不是自動的，做法是掃事件的 `cause`
裡有沒有「自動」兩個字。

```python
auto = sum(1 for e in ev if e["kind"] == "DISPATCH"
           and "自動" in (e["cause"] or ""))
```

兩個方向都會錯。呼叫端自己給了 `cause`（例如「owner 已決定」）時，
那一次真的自動派工會從指標裡消失；反過來，手動派工的理由裡只要
寫到「自動」就會被誤算。

而它會退化成猜字串，是因為 `events_of()` 的 SQL 根本沒有 SELECT
`payload` —— 指標拿不到它要的欄位。

修法是三處一起：`events_of()` 帶出 payload、`dispatch()` 收一個
明確的 `auto` 旗標寫進 payload、`continuity()` 讀旗標。

### 11.3　第二個錯：分母是 0，分數算出 3.0

接上之後第一次真的拿它跑一件真實任務，三步全自動走完，然後印出：

```
自動接上　3 / 0
連續性分數　3.0
```

分數是比例，不該超過 1。分母是 0，因為舊定義是
`PROGRESS_REPORT + WORKER_RESULT`，而 `drain()` 走的是
派工 → 驗證 → 派下一步，兩種事件都不產生。

規格 F06 §5 只給了公式，沒有定義 `ExpectedContinuation` 數什麼。
所以新的分母是我的詮釋，跟 `STALL_RISK` 的四因子同一個性質，
已在 `continuity()` 的 docstring 標明：

```
ExpectedContinuation = 「步驟驗證通過且任務還有下一步」的次數
                     + 進度報告次數

AutoContinued        = 自動派工次數，扣掉任務的第一次派工
```

扣掉第一次是因為那是起步不是接續，前面沒有東西可以接。不扣的話，
一個只有一步的任務會看起來完美自動，而它從沒接續過任何東西。

刻意不算 `WORKER_RESULT`：worker 交回結果之後的那次繼續，已經被
「驗證通過就派下一步」涵蓋，兩邊都算會讓同一次交接被數兩次。

**這兩個錯都只有在真的用它的時候才會出現。** 142 條測試全過，
沒有一條發現分母是 0，因為測試都走 `submit_result()` 那條路，
而 `drain()` 不走。一個沒有人用過的指標，會安靜地算出離譜的數字。

### 11.4　驗收

用一支腳本當驗收條件，動手前後各跑一次：

```bash
python3 tools/check-auto-continuity.py
```

它問的問題跟單元測試不同。單元測試問「它會不會動」，這支問
「它有沒有真的被用過」。

```
動手前   派工 8 筆，自動 0，有人推的 8      exit 1
動手後   派工 11 筆，自動 3，有人推的 8     exit 0
```

那件任務本身也記在帳本裡（`T-eb34677986`），三步都是
`VERIFIED_COMPLETE`，`HumanContinueBurden` 是 0。整條鏈跑完的過程
沒有人說過一次「繼續」。

### 11.5　還留著的一項待校準

任務終止之後寫的進度報告仍然會計入分母，而那時已經沒有東西可以繼續。
所以 `T-eb34677986` 收尾時補記兩則發現，分數就從 1.0 掉到 0.5。

**沒有當場改。** 同一天已經動過一次分母定義，第三次要有實測資料
支撐，不是靠直覺。目前只有兩件真實任務，樣本不足。這一項已經用
`report()` 記進帳本，不是留在某個人的記憶裡。
