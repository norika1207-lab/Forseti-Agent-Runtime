### 第 28 節　宣稱階段完成之前的 AI 自我審計（行 1005-1016）

十個必答題：

- 行 1007　我宣稱通過的出口閘門，確切是哪一個。
- 行 1008　每一條閘門條件的確定性證據在哪裡。
- 行 1009　有沒有混淆 written、running、completed、verified、releasable。
- 行 1010　有沒有加上北極星或擁有者沒授權的限制或需求。
- 行 1011　最近的更正或反證有沒有讓現在計畫的某部分失效。
- 行 1012　我保留舊答案，是因為它的前提仍然成立，還是只因為它看起來連貫。
- 行 1013　哪些是我親自驗證的，哪些只是轉述別的 agent 或 session。
- 行 1014　有沒有在一個索引或窗口就夠用的地方，用掉一整個 session。
- 行 1015　我的工作有沒有讓 Forseti 更侵入或更慢，量到的 overhead 是多少。
- 行 1016　如果這個 session 現在死掉，給後繼者的最小確切下一步是什麼。

### 第 29 節　POC Done 的定義（行 1018-1031）

- 行 1020　POC 只有在下列情境能對真實或擷取的歷史 session「端到端展示」時才算完成。
- 十個條件：
  - 行 1022　從至少一個真實 provider/harness 把 session 收進 raw + normalized 的耐久事件。
  - 行 1023　顯示 event-only 溫度與分開的健康維度隨時間變化。
  - 行 1024　不做全 session 語意讀取就定位出可疑窗口。
  - 行 1025　用針對性的語意分析，把至少一種協作或 runtime 病理分類出來，附證據參照。
  - 行 1026　區分活動與已驗證進度，算出資源燒耗。
  - 行 1027　把一次更正或反證正規化成事件，並讓依賴它的假設或計畫分支失效。
  - 行 1028　產出一份救援建議或 clean-fork 包，排除已失效或被污染的節點。
  - 行 1029　在 X-Ray 裡呈現這次事故，帶信心與證據標籤。
  - 行 1030　在正常 session 上展示量測到的 overhead 與打斷行為。
  - 行 1031　一個全新 AI session 能只靠專案檔案接手開發，不依賴對話記憶。

### 第 30 節　POC 之後的產品定位（行 1033-1037）

- 行 1035　一開始不要把自己賣成通用治理儀表板。對開發者的承諾要具體：
  安靜地偵測 AI 協作開始退化、顯示原因、阻止死策略燒時間與配額、
  幫使用者復原有生產力的工作而不失去專案關係與 context。
- 行 1037　長期上 Code Duo + Code Tree + Forseti 組成 AI 原生的軟體工程作業層：
  持久的協作者、持久的專案因果、runtime 保障。底層模型與 harness 可以換，
  已驗證的專案關係與連續性留下來。

### 第 31 節　立即的第一個建置 sprint（行 1039-1056）

- 行 1039　十四個「工作步」，不是日期。
- 行 1041-1056　每一步有確切產出與「沒達成不准繼續」的條件：

### 第 32 節　AI 現在還不准做的東西（行 1058-1066）

- 行 1060　單一 session 的擷取與重播還沒能動之前，不做龐大的多 agent 架構。
- 行 1061　raw/normalized 事件與證據語意還不可靠之前，不做漂亮的圖形 UI。
- 行 1062　確定性的歷史重播與獨立標註存在之前，不做預測性 ML。
- 行 1063　開發者 POC 證明淨生產力增益之前，不做企業 SSO、RBAC、control plane。
- 行 1064　不做通用人格模型。從明確可檢視的互動 profile 訊號開始。
- 行 1065　不做預設上傳原始私有 session 的中央雲。
- 行 1066　不做只憑溫度、情緒、編輯次數或單一 heuristic 的硬阻擋。

### 第 33 節　最終 AI 指令（行 1068-1072）

- 行 1070　由下往上建：先觀察現實、再量化健康、再定位需要語意的地方、
  再只解讀必要的窗口、再區分進度與活動、再讓更正撤銷過期權威、再救援。
  這些全部證明之後，Forseti 才可以變得更聰明、更會預測、更有控制力。
- 行 1072　使用者要感覺 Forseti 是桌上的溫度計加上需要時的救援系統，
  不是另一個討注意力的經理。健康工作時 AI 自由跑；證據顯示協作變成迷宮時，
  Forseti 能保住工作、恢復人的主導權、讓專案動起來。

## 三、衝突或矛盾

1. 【§27 的 HANDOFF 模板 vs repo 已明文否決 handoff.md 產生器】
   `DECISION_LEDGER.md` 行 162-163：「先做一個 handoff.md 產生器。否決理由是
   那還是塞……這條路先前試過，撐不過六個 session。」`bible.md` H-01（行 257-263）
   記著她的原話：handoff 是文字就會失效，要是可驗證狀態。
   這跟 §27 要求每個 session 產出一份文字模板正面相對。
   緩解的是行 1003 書自己也說交接不是證據的替代品、後繼者必須查證據，
   所以精神上兩邊一致（不能只靠文字），分歧在形式：書要一份模板檔，
   repo 選了控制檔集合 + doctor + 帳本。這個分歧目前沒有 ADR 記載
   「我們用什麼取代 §27 模板、模板裡哪幾欄因此沒人記」。上面列的七個
   無人記錄欄位（stop_condition、prohibited_claims 等）就是這個缺口的實際後果。

2. 【§32 行 1060 與 §33 的順序 vs F 線先做了執行與派工層】
   書說單一 session 的 capture/replay（步 3-5）能動之前不做多 agent 架構，
   §33 說先觀察現實再談控制。repo 的實際順序是：F01-F08
   （ledger、worker、watchdog、跨 session 派工）已 `VERIFIED_COMPLETE`
   （`PHASE_STATUS.md` 行 153-170），而事件擷取與重播（階段 1）`NOT_STARTED`。
   事實脈絡：F 線出自另一份 owner 提供的九份 modular spec
   （`REQUIRED_READING.md` 行 159-169，各有 hash，READ_COVERAGE=FULL），
   不是 AI 私自加的方向。所以這是「兩份規格的優先序衝突」，不是違紀。
   但 `DECISION_LEDGER.md` 的六條 ADR 標題裡（grep 過）沒有一條記載
   「F 線為什麼先於工程書的步 3-5」這個順序決定。工程書行 22 說不准默默
   重新詮釋階段順序，這個決定現在就是沒被記錄的狀態。

3. 【§32 行 1061 禁 UI vs repo 裡有兩個 HTML】
   `docs/design/thermostat.html`（設計稿）與 `tools/dashboard.html` +
   `tools/dashboard.mjs`（`.forseti/state.json` 的被動唯讀鏡，
   `tools/README.md` 行 205-211）存在，而 `docs/build-plan.md` 行 233 寫
   「任何 UI（含 X-Ray 畫面）」不做，理由正是引工程書 Phase 0 的禁令。
   dashboard 唯讀、不寫入、不對被觀測 session 送東西，跟書擔心的
   「在事件語意可靠前做漂亮圖形 UI 」不是同一個量級，但形式上跟
   build-plan 自己的禁令牴觸。這要 owner 裁決：是補一條 ADR 把
   「被動唯讀鏡」明文豁免，還是收掉。

4. 【§31 步 2 指定 Pydantic vs repo 的零依賴哲學】
   `ledger.py` 檔頭明寫「零依賴。sqlite3 是標準庫」，現有 Python 全部
   走標準庫，repo 裡沒有任何 pydantic。書明文指定 Pydantic schemas。
   這個衝突還沒發生（階段 1 未動工），但動工那天要嘛引入依賴、
   要嘛記 ADR 說明偏離，不能默默二選一。

5. 無衝突處：§28 十題、§29 十條、§30 定位、§33 的姿態，
