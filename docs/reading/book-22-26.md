## 一、這幾節規定了什麼

### 第 22 節 Runtime Health Model(行 841-858)

1. 行 843-854(22.1):健康分八個維度,每個維度有自己的訊號與解讀方式:
   - Context(行 847):窗口壓力、無關殘留、矛盾密度。只代表 context 可能變得沒用,不是失敗的證明。
   - Tool/Runtime(行 848):時長、重試、逾時、工具對產出比、orphan/stall。
   - Progress(行 849):已驗證的狀態轉移、產物、解除的 blocker。
   - Collaboration(行 850):糾正、微管理、目標重述、QA 負擔。
   - Evidence(行 851):宣稱驗證、過期來源、缺口。
   - Strategy(行 852):反證下仍用同一假設、重複戰術。
   - Resource(行 853):token、時間、API、人被打斷的次數對比進度。
   - Continuity(行 854):checkpoint 年齡、交接是否足夠、事件缺口。
2. 行 856-858(22.2):單一溫度只是 UX 摘要。內部每個維度必須各自可查詢,不准太早合併,因為 context 壓力、過期證據、工具死鎖、協作倒置、計畫失效各自的解法不同。

### 第 23 節 First Divergence 與健康基線重建(行 860-874)

3. 行 862:Forseti 必須同時重建病理與健康。接手者要知道劣化之前正常有生產力的工作長什麼樣,不是只看被污染的結局。
4. 行 864-870(23.1):三個分歧標記,各自定義不同:
   - Earliest possible divergence(行 868):第一個「可能」開啟劣化的事件或窗口。
   - Earliest confirmed divergence(行 869):第一個有足夠證據判成真實違規或失敗的事件。
   - First consequential divergence(行 870):之後下游工作實質改變或被污染的第一個點。
5. 行 872-874(23.2):每個 session 要找出早期「已驗證進度強、工具對產出正常、糾正負擔低、目標一致」的窗口,存成健康基線指紋。之後的異常分數部分拿 session 自己當對照,減少對全域門檻的依賴。

### 第 24 節 歷史事故 fixture 要求(行 876-899)

6. 行 878-885:六種事故 fixture,各自規定必備內容:
   - Blank/tool loop(行 880):原始工具事件、可見輸出、cancel/ESC、最終復原、token/時間。
   - False completion(行 881):assistant 的宣稱、檔案與程序的現實、之後的更正。
   - OCR/session reconstruction(行 882):最後健康 checkpoint、context 飽和、不完整交接、接手者飄移、之後的復原證據。
   - Resource burn / URL incident(行 883):目標、未授權限制、反證、重複策略、token 成本進度時間線。
   - Advertising plan-salvage(行 884):推測的意圖、量化假設、素材更正、授權更正、計畫血緣。
   - Code migration / human-as-QA(行 885):原始功能集、遷移動作、漏掉的 QA、人的糾正、最終結果。
7. 行 887-897(24.1):五個證據等級:PRIMARY_RAW(行 889)、VERIFIED_RUNTIME(行 891)、DERIVED_SUMMARY(行 893)、AGENT_SELF_AUDIT(行 895)、HUMAN_RECOLLECTION(行 897)。
8. 行 899:低等級證據可以引導搜尋,但不得冒充缺失的一手證據。

### 第 25 節 測試策略(行 901-915)

9. 行 903-911:七個測試層級,各層必測項目:
   - Unit(行 905):schema、狀態轉移、溫度特徵、失效傳播、進度記帳。
   - Contract(行 906):provider adapter fixture、事件正規化、resume cursor、能力宣告。
   - Replay(行 907):歷史事故要能重放出穩定的 events/windows/health/decisions。
   - Integration(行 908):daemon 重啟、session 替換、檔案程序驗證、checkpoint 復原。
   - Chaos(行 909):殺掉 importer/daemon、截斷事件、弄壞 cache、時鐘偏移、orphan 程序。
   - Productivity(行 910):runtime 開銷、打斷率、誤報、開發者完成時間。
   - Research(行 911):盲測 holdout(依專案、時間、失敗家族切)、信心校準。
10. 行 913-915(25.1):拿來設計偵測器的歷史事故是回歸 fixture,不是偵測器泛化的證明。泛化宣稱需要獨立的 holdout 事故。

### 第 26 節 淨生產力增益(行 917-946)

11. 行 919-932:NPG 公式 = 避免的重工時間 + 省下的復原時間 + 避免的資源燃燒 + 避免的不可逆錯誤成本,減去驗證延遲、打斷時間、誤報成本、治理開銷。
12. 行 934:如果 Forseti 抓到很多異常,但一般開發者因為它拖慢或嘮叨而關掉它,產品就是失敗。可靠性必須比失敗便宜。
13. 行 938-945(26.1):六個 runtime 模式:OBSERVE(行 940,量測儲存,除了本地硬安全不變式外不同步阻擋)、ASSIST(行 941,強劣化才低噪音介入)、GOVERN(行 942,高風險工作強制權限與 commit 邊界)、FORENSIC(行 943,證據保全優先,可凍結變更)、RECOVERY(行 944,救援 checkpoint、乾淨分叉、接管包)、EXPERIMENT(行 945,把有生產力的異常或替代計畫隔離出去)。

## 三、衝突或矛盾

1. 證據分級三套並存,和書上的五級都對不齊。書 24.1(行 889-897)是五級;`src/evidence.js:36` 是 v2 四級(OBSERVED/DECLARED/INFERRED/MISSING);`src/conformance.js:32` 是 v1 的 EPISTEMIC 序列;`tools/save-case.py` 又用了第四套的 `MODEL_SELF_REPORT`(概念接近書上的 AGENT_SELF_AUDIT,但名字不同)。evidence.js 檔頭(行 11-17)自己已經承認 v1 和 v2 講的是不同的東西。四套的精神一致(低級不得冒充高級),但如果之後要照書實作 fixture,五級和現有分級的對映必須先決,否則同一份材料會有兩個等級標籤。
2. NPG 公式與 overhead.js 的設計哲學直接矛盾。書行 919-932 要求把效益與成本加減成一個淨值;`test/overhead.test.mjs` 檔頭第二行明寫「負擔可以量,效益只能估,而這個模組拒絕把兩者相減」。這不是漏做,是 repo 端刻意做了相反的決定。哪邊贏需要 owner 裁決:照書實作 NPG,就得推翻 overhead.js 的拒絕;維持 overhead.js 的立場,書的 NPG 就要降級成概念框架而不是要算的數字。
3. 健康模型的本體論不同:書是八維度(行 843-854),repo 是十訊號(`src/signals.js` 的 S1-S10,照 spec v0.1 §3.1「一字不改」)。兩者可以對映(例如 S10 落在 Strategy 維度、S1/S4 落在 Tool/Runtime 維度),但目前沒有任何對映存在。這是張力不是打架:22.2「分開可查、不早合併」的精神 runtime.js 已經做到了,差的是維度這一層的分組。
4. 名字撞車風險:書 26.1 的六個「模式」(OBSERVE/ASSIST/...)與 `src/intervention.js:36` 的六個「動作」(QUIET_ANNOTATION/SUGGEST_RECOVERY/FREEZE_RETRY/REPLAN/BLOCK_HIGH_RISK/CREATE_SUCCESSOR)是不同層的東西:模式是系統的常駐姿態,動作是單次介入。兩邊都是六個,後續實作很容易混為一談。實作模式機時要把動作掛在模式底下(例如 ASSIST 模式才允許 SUGGEST_RECOVERY),不是把動作改名成模式。
