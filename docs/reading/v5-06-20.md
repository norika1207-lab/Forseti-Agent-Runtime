## 一、這兩節規定了什麼

### §6 Event Ledger and Lineage Ledger（171-210 行）

1. 雙重事件表示（173-175 行）：每一個 provider 原生事件都要存兩份，raw 一份、
   normalized 一份。正規化永遠不准破壞原始證據。
2. RawEvent 結構（177-179 行）：`id, provider, provider_event_type, timestamp,
   payload_hash, payload`。
3. NormalizedEvent 結構（181-184 行）：`id, raw_event_id, project_id, agent_id,
   session_id, runtime_node_id, type, action, subject, object, result, provenance,
   risk, metadata`。每筆正規化事件要能指回它的 raw 事件。
4. Canonical 事件型別八大類（186-197 行）：Cognitive（190 行，USER_INSTRUCTION、
   MODEL_OUTPUT、ASSUMPTION 等）、Tool（191 行，TOOL_CALL、TOOL_RESULT、RETRY 等）、
   Artifact（192 行，FILE_READ、FILE_WRITE、DB_WRITE 等）、Runtime（193 行，
   PROCESS_START、NODE_HEARTBEAT、SESSION_RESUME 等）、Workflow（194 行，STEP_START、
   STEP_COMMIT、STEP_ROLLBACK、APPROVAL_REQUESTED）、Governance（195 行，POLICY_ALLOW、
   POLICY_BLOCK、WRITE_BARRIER 等）、Recovery（196 行，CHECKPOINT、INCIDENT_OPEN、
   TAKEOVER 等）、Health（197 行，CONTEXT_SAMPLE、QUEUE_DEPTH、TOOL_LOOP 等）。
5. Lineage 邊十種（199-210 行）：DERIVED_FROM（201）、TRIGGERED_BY（202）、
   VERIFIES（203）、REFUTES（204）、SUPERSEDES（205）、CONSUMES（206）、
   PRODUCES（207）、PROMOTES（208）、PROPAGATES_TO（209）、RECONSTRUCTED_FROM（210）。
   把決策、證據、宣稱、工具呼叫、產物、事故之間的因果串成圖。

### §20 Storage Architecture（528-566 行）

6. Canonical 專案目錄（530-554 行）：`.forseti/` 底下要有 `project.json`（533）、
   `north_star.json`（534）、`source_of_truth.json`（535）、`runtime_topology.json`（536）、
   `policies.yaml`（537）、`session_registry.json`（538）、`model_profiles.json`（539）、
   `trust_ledger.json`（540）、`event_ledger.jsonl`（541）、以及十三個子目錄：
   `raw_events/`（542）、`evidence/`（543）、`claims/`（544）、`checkpoints/`（545）、
   `snapshots/`（546）、`executions/`（547）、`workflows/`（548）、`incidents/`（549）、
   `reconstruction/`（550）、`dialogue/`（551）、`decisions/`（552）、`environment/`（553）、
   `probes/`（554）。
7. 資料庫表清單（556-562 行）：二十八張表，含 `events`、`raw_events`、`claims`、
   `evidence`、`decisions`、`lineage_edges`、`workflows`、`workflow_steps`、
   `checkpoints`、`heartbeats`、`incidents`、`policies`、`probes` 等。
8. 儲存實作建議（564-566 行）：P0 用 SQLite WAL 模式，本機優先、單專案 daemon，
   外加 append-only JSONL 匯出以利可攜。schema 要有 migration 控管。之後的
   server 版可換 PostgreSQL 但 domain contract 不變。大型 raw payload 與產物
   用內容定址（content-addressed）放磁碟或物件儲存，關聯式帳本只存參照。

## 三、與已實作的東西有沒有衝突

有三處。前兩處是真衝突，第三處是命名與格式的分歧。

### 衝突一　`events` 表名已被派工事件佔用（就是待裁決第二條）

§20.2（559 行）要求資料庫裡有 `events` 與 `raw_events` 兩張表，裝的是 §6 的
provider 行為事件。但 ledger.py:163-168 的 `events` 表已經存在，裝的是派工協調
事件（WORKER_ACCEPTED 等八種加控制端紀錄），欄位是
`at, task_id, step_id, kind, from_state, to_state, cause, actor, payload`，
與 §6.1 NormalizedEvent 的十四個欄位完全對不上。照 §20.2 在同一個庫建表會直接撞名。
詳細分析見本檔最後一節（乙）。

### 衝突二　§20.1 的「一切放 .forseti/」撞上 exFAT 的實測限制

§20.1 把整個儲存體系放在專案目錄 `.forseti/` 底下，§20.3 的 SQLite 也預設
local-first。但這個 repo 在 exFAT 外接碟上，ledger.py:236-252 記了實測結果：
sqlite 需要的 POSIX advisory lock 在 exFAT 上沒有，寫入報
「attempt to write a readonly database」，所以帳本已經被迫搬到
`~/.forseti/ledgers/<專案名>-<hash>.db`。任何照 §20 字面把 SQLite 建回
`.forseti/` 的嘗試都會重蹈。JSONL 純 append 不受此限（普通檔案寫得進去，
ledger.py:241 有記），所以 `event_ledger.jsonl` 放 `.forseti/` 可行，
資料庫不行。做 §20 的時候必須把這個環境事實寫進去，不是照抄目錄圖。

### 衝突三　控制檔命名與格式已定案且與 §20.1 不同

repo 已經用 `NORTH_STAR.md`（人讀 markdown）而不是 §20.1 的 `north_star.json`
（534 行），用 `goal.json` 而不是 `project.json`（533 行），而且 ADR-005
（DECISION_LEDGER.md:96-108）已裁定這批控制檔進版控、執行期狀態不進。
現有工具（doctor、hook、離題偵測）讀的是現在這套名字。照 §20.1 改名會斷工具，
不改名則與 §20.1 字面不符。這需要一條 ADR 記「本專案用哪套名字對映 §20.1
哪個檔」，屬於待補文件，不是誰對誰錯。

沒有發現的衝突：§20.3 的 migration 控管與 ledger.py 的自製 migration 不衝突
（後者就是前者的零依賴版）；append-only 原則兩邊一致。

## 甲、這兩節合起來對「階段 1 事件帳本」的要求

把 §6 與 §20 疊起來，階段 1 的事件帳本要滿足這些才算照 v5.0 做：

1. 每個 provider 原生事件存兩份：raw 進 `.forseti/raw_events/`（542 行），
   normalized 進帳本，正規化不得破壞原始證據（175 行）。
2. Raw 事件帶 `payload_hash`（178 行），大 payload 內容定址外存、帳本存參照
   （566 行）。
3. Normalized 事件要有 `raw_event_id` 指回原始事件，並帶
   project/agent/session/runtime_node 四層歸屬與 provenance、risk 欄
   （181-184 行）。
4. 事件型別要落在 §6.2 的八大類 canonical types 裡（186-197 行），
   不是自由字串。
5. 事件之間、事件與決策證據宣稱之間的因果，用 §6.3 的十種 lineage 邊存成
   `lineage_edges`（199-210 行、560 行）。
6. 儲存形式：SQLite WAL 模式為主、append-only JSONL
   （`.forseti/event_ledger.jsonl`，541 行）為可攜匯出，schema 有 migration
   控管（564-566 行）。
7. 帳本在資料庫層對應 `events` 與 `raw_events` 兩張表（558-559 行），
   與 `lineage_edges` 一起構成完整的事件加因果紀錄。

repo 現況對著這七條：第 6 條有一半（SQLite 有、migration 有，但 WAL 沒開、
JSONL 沒有），其餘六條都還沒開始。另外第 6 條的「SQLite 放本專案」在這顆
exFAT 碟上做不到，實作時要沿用 ledger.py 已踩出來的 home 目錄方案或另裁。

## 乙、§6 的 event ledger 是哪一種（直接回答待裁決第二條需要的資訊）

**答案：v5.0 §6 的 event ledger 是 provider 行為事件那一種，跟 AI-First 工程書
Phase 1 的 event ledger 同種，不是 `ledger.py` 的派工協調事件。**

證據，全部是源檔原文：

1. 175 行第一句就是「Every provider-native event is stored twice」，
   ledger 的內容物定義為 provider 原生事件。
2. RawEvent 的必要欄位是 `provider, provider_event_type`（177-179 行）。
   派工事件沒有 provider，這個結構裝不了它。
3. §6.2 的分類（190-197 行）是 AI 與 runtime 的行為：使用者指令、模型輸出、
   工具呼叫、檔案讀寫、process 起停、政策放行阻擋。與工程書 445-450 行的六類
   （Dialogue / Tool / Runtime / Artifact / Usage / Governance）是同一族，
   v5.0 多了 Cognitive、Workflow、Recovery、Health 四類，範圍更大但同種。

所以待裁決第二條描述的撞名是真的：工程書與 v5.0 講的 event ledger 是同一種
東西（provider 行為事件），而 `ledger.py` 的 `events` 表（ledger.py:163-168）
是另一種東西（派工協調），兩者不能混。

但有一個會直接影響裁決方向的細節，裁決前要知道：

**v5.0 自己的設計是「單一帳本容納兩類，用分類與分表區隔」，不是分庫。**
§6.2 的八大類裡有一個 Workflow 分類（194 行：STEP_START、STEP_COMMIT、
STEP_ROLLBACK、APPROVAL_REQUESTED），這些正是派工協調那一族的事件；
§20.2 又把 `workflows`、`workflow_steps` 與 `events`、`raw_events` 列在
同一個資料庫裡（558-559 行）。也就是說照 v5.0 走，派工步驟事件會以
Workflow 分類進同一本 normalized 帳，任務與步驟本身另有 `workflow_steps` 表。

這對裁決的實際影響：

1. 如果選「照 v5.0 合一」：ledger.py 的 `tasks`、`steps` 大致對應 v5.0 的
   `workflows`、`workflow_steps`，它的 `events` 表就得改名或改造成 §6.1 的
   NormalizedEvent 結構，現有欄位對不上，等於重寫加資料遷移。
2. 如果選「分開」（不同庫或不同表名加文件明示）：與 v5.0 §20.2 的單庫清單
   字面不符，但保住已實測過的派工帳本不動。而且實體上已經半分開了：
   派工帳本因 exFAT 限制在 `~/.forseti/ledgers/`（ledger.py:236-252），
   行為事件帳本照 ADR-003 是 `.forseti/event_ledger.jsonl`，兩者本來就不在
   同一個地方。
3. 不管選哪邊，「`events` 這個名字給誰」都必須寫成 ADR。現在的風險
   （DECISION_LEDGER.md:235-238 描述的兩種誤用）只要沒有明文就會持續存在。

本節只提供事實，選哪邊是 norika 的裁決，這裡不代決。
