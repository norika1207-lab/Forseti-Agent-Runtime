## 一、這幾節規定了什麼（附行號）

### 第 0 節　AI 怎麼用這本書（行 20-71）

- 行 22　這份文件是專案的 control plane。AI 可以在現實逼迫下提 ADR，但不准默默重新詮釋北極星、合併階段、用自我報告取代要求的證據、或最佳化還沒過前置閘門的功能。
- 行 24-32　每個新 session 的強制啟動流程，七步：
  1. 改 code 之前先讀第 1 到 7 節（行 26）。
  2. 讀當前的 PHASE_STATUS.md、DECISION_LEDGER.md、BLOCKERS.md、最新的 HANDOFF.md（行 27）。
  3. 用一段話講出北極星，指出現在是哪個階段（行 28）。
  4. 講出這個階段的確切出口閘門，列出已有與缺少的證據（行 29）。
  5. 在宣稱實作狀態之前先檢查 repository 與 runtime（行 30）。
  6. 只做推進當前階段或解除已驗證阻塞的工作（行 31）。
  7. 結束前寫出耐久的 artifacts 與最小交接契約，對話裡的文字不算耐久的專案狀態（行 32）。
- 行 34-49　十二條不可談判的 AI 行為契約：
  - AI-01（行 38）　不准隱性改變產品目標，改要 ADR 加擁有者同意。
  - AI-02（行 39）　一次只有一個 active phase，後面階段的功能只在介面需要時打 stub。
  - AI-03（行 40）　「我實作了」不是證據，要拿測試、hash、diff、程序狀態、fixture 結果這種確定性證明。
  - AI-04（行 41）　WRITTEN、RUNNING、COMPLETED、VERIFIED、RELEASABLE 是不同狀態，不准跳。
  - AI-05（行 42）　不准藏不確定性，UNKNOWN 就是 UNKNOWN，沒被禁止不等於被允許。
  - AI-06（行 43）　使用者的更正或更強的反證必須先讓依賴它的假設與計畫失效，才能繼續執行。
  - AI-07（行 44）　核心前提被推翻後不准搶救舊計畫，要從已驗證的現實重新規劃。
  - AI-08（行 45）　昂貴的重試沒有帶來已驗證進度時，凍結策略、重新規劃，不准繼續燒 token 與時間。
  - AI-09（行 46）　不准讓人類當 QA，AI 自己能跑的測試與檢查要先跑完才報完成。
  - AI-10（行 47）　不准把重要狀態、理由、更正、下一步只放在一個對話 context 裡。
  - AI-11（行 48）　預設觀察、最小打擾。讓正常開發變慢變吵，本身就是產品失敗。
  - AI-12（行 49）　不准依賴隱藏思維鏈，只用可觀測的事件、輸出、工具軌跡、更正、artifacts、明確決定。
- 行 51-71　標準階段執行迴圈：讀當前狀態、驗證 repo 與 runtime 現實、重述階段與出口閘門、選最小的未阻塞任務、實作、跑測試或 fixture、記錄證據、更新階段狀態，閘門過了才照契約轉移，沒過就留在同階段或記阻塞。

### 第 1 節　北極星與核心比喻（行 73-94）

- 行 75　Forseti 是安靜的 runtime 協作健康與復原基底，第一個介面是溫度計，平常不出聲，溫度升高時使用者可以問為什麼。
- 行 79　北極星：讓人加 AI 的工作在模型變被動、工具狂打、重複、context 退化、誤導、卡死時，仍然有生產力、可理解、可復原、可延續。使用者不該變成 AI 的保母、QA 部門、或手動復原機制。
- 行 81-88　四層使用者體驗：Temperature（一個安靜的健康指標，不宣稱診斷）、X-Ray（顯示可觀測的 pattern 與候選的第一個分歧點）、Evidence（區分 OBSERVED、DECLARED、INFERRED、COUNTERFACTUAL）、Rescue/Control（在 policy 允許下建議或執行最不侵入的復原）。
- 行 90-94　控制哲學：量測、偵測、解釋、升級、必要時才介入。高溫不是診斷，分歧不自動等於失敗，探索可能產生有用的發現。

### 第 2 節　Forseti 要解的問題（行 96-108）

行 98-108 列了九個問題家族，每個都配症狀與要求的結果：

- 行 100　Runtime 衰退：回答變短變散、工具呼叫佔滿、跑 10-30 分鐘沒有有用輸出。要在人類猜要不要按 ESC 之前偵測到。
- 行 101　輸出飢餓與空白迴圈：工具還在跑但使用者看到的回應一直是空白。要分類工具佔用與存活狀態，提供純對話救援。
- 行 102　人類變 QA：使用者一直指出缺功能、半套遷移、明顯不一致。要量測人類更正密度，偵測角色反轉。
- 行 103　資源燒毀：大量 token 與時間沒有換到耐久已驗證的進度。要追蹤成本對進度比，停掉重複無進度的策略。
- 行 104　Session 死亡：長 session 結束後，接手者只從摘要開始，遺失決定背後的因果。要把因果 context、決定、互動模式、最後已知良好狀態保存在 session 之外。
- 行 105　被推翻的假設還有權威：反證已證明介入層錯了，agent 還照舊行動。要撤銷假設權威並要求重新規劃。
- 行 106　失效的計畫還有權威：核心資產或能力假設垮了，AI 還在搶救舊計畫。要讓依賴節點失效並跨過 Replan Boundary。
- 行 107　假完成：AI 說遷移完了、檔案改了，卻沒查實際狀態。要有宣稱對證據的驗證與狀態晉升閘門。
- 行 108　Context 與語意污染：session 後段的怒氣、更正、工具噪音被接手者當成專案的最佳摘要。要找出健康與因果的區間，從證據重建而不是只摘要結尾。

### 第 3 節　明確的非目標與邊界（行 110-119）

- 行 112　Forseti 不是替代的 coding agent、IDE、orchestration 框架、Git、CI/CD、或模型路由器。
- 行 113　不承諾讀隱藏思維鏈，也不准需要它。
- 行 114　不擋每個動作，不對普通可逆工作強制人類確認迴圈。
- 行 115　不把髒話、挫折、情緒語言等同技術失敗，語言訊號只能配合行為與更正證據使用。
- 行 116　不把整個 session 塞進一個 LLM context，先索引再縮小，語意解讀是針對性的。
- 行 117　不把摘要當完整專案記憶，摘要是導航輔助不是 lineage 的替代品。
- 行 118　agent 自我稽核在事件或 runtime 證據佐證之前不得封為真相。
- 行 119　不最佳化警報數量，最佳化 Net Productivity Gain 與被找回的人類主導權。

### 第 4 節　系統成功判準（行 121-133）

- 行 125　被動可觀測性：正常 coding 流程開著 Forseti 跑，不需要使用者互動。
- 行 126　熱路徑開銷：普通低風險事件處理目標 p95 小於 50 毫秒，語意分析預設非同步。
- 行 127　打擾率：Observe 與 Assist 模式下同步介入目標低於普通動作的百分之一，門檻用真實 session 校準。
- 行 128　事件完整性：已知的攝取缺口用 EventGap 明確表示，缺口兩側不准默默宣稱完整因果。
- 行 129　復原有用性：對歷史工具迴圈與死 session fixture，Forseti 找到的停止點要早於當初人類介入的時間點。
- 行 130　進度保護：重複花費卻沒有已驗證進度的策略要開 burn incident，停止無上限重試。
- 行 131　更正傳播：推翻核心前提的更正，要在後續受管制執行之前讓依賴的計畫與假設節點變 stale 或 invalid。
- 行 132　連續性：接手者不用注入完整 transcript 就能重建目標、已接受的決定、最後已知良好狀態、未解的未知、互動輪廓。
- 行 133　人類效用：使用者不讀原始 log 就能回答健康嗎、為什麼、什麼變了、接下來做什麼。

### 第 5 節　正典架構（行 135-203）

- 行 137-195　資料流：Provider 或 harness 進 Capture Plane，進 append-only 的 Event 加 Lineage Ledger，再分流到 Fast Health Engine（確定性統計，不需要 LLM）、Suspicious Window Locator、Semantic Sampler（只取目標 chunk）、Collaboration/Intent Analyzer、Reality 加 Progress Engine、Correction/Hypothesis/Plan Graph、Resource Burn Guard、Recovery/Takeover/Continuity，最後到 X-Ray 加 Temperature UI，配 Observe、Assist、Govern、Forensic、Recovery 五種模式。
- 行 197-203　熱路徑冷路徑分離。熱路徑只准做時間戳、計數器、本地狀態查詢、確定性 policy、append 事件、便宜的異常特徵，禁止每個事件都呼叫 frontier LLM、禁止語意分析時擋普通編輯（行 201）。溫路徑做視窗聚合、指紋、基本序列偵測、證據新鮮度、資源記帳，禁止昂貴的全 session 解讀（行 202）。冷路徑做針對性語意分析與因果假設，禁止把推論的因果假裝成確定性真相（行 203）。

### 第 7 節　正典 domain model（行 314-352）

- 行 316-324　二十六個 domain 概念：Project、Agent、Session、RuntimeNode、Event、RawEvent、Resource、Claim、Evidence、Decision、Correction、Hypothesis、Plan、PlanStep、MetricRecord、HealthSample、SuspiciousWindow、CollaborationSample、ProgressRecord、ResourceCostRecord、BurnIncident、Checkpoint、Incident、Handoff、InteractionProfile、EventGap、PolicyDecision。

- 行 342-352　7.2 節必要的 epistemic 標籤五級：OBSERVED（確定性或 runtime 證據）、DECLARED（人或模型明講的）、INFERRED（Forseti 的分析，非直接證據）、COUNTERFACTUAL（replay 或 ablation 支持因果效應）、UNKNOWN（證據不足）。

### 第 8 節　開發路線圖（行 354-371）

行 356-371 列出十三個階段（0 到 12），每階段回答一個主問題：

- 階段 0（行 358）　Bootstrap 與契約：每個 AI session 能不能從同一份已驗證的專案契約開始。
- 階段 1（行 359）　擷取與可重播事件帳本：能不能不做語意解讀就觀測 session。
- 階段 2（行 360）　Runtime 溫度計 v0：簡單事件特徵能不能分出正常與明顯退化。
- 階段 3（行 361）　可疑視窗定位器：能不能不載入整個 session 就找到要看哪裡。
- 階段 4（行 362）　針對性語意加協作健康：只用選出的視窗能不能偵測人類當 QA、被動 agent、更正迴圈。
- 階段 5（行 363）　現實、進度與燒錢守衛：能不能區分活動與已驗證進度並保護配額與時間。
- 階段 6（行 364）　更正、假設與計畫權威：新資訊能不能撤銷過時的計畫與假設。
- 階段 7（行 365）　救援與復原引擎：能不能安全地把使用者從失敗的協作狀態救出來。
- 階段 8（行 366）　X-Ray v1 加溫度 UI：人類能不能不做 log 考古就看到健康、原因、介入、復原。
- 階段 9（行 367）　連續性記憶與互動 context。
- 階段 10（行 368）　Code Duo 整合。
- 階段 11（行 369）　Code Tree 整合。
- 階段 12（行 370）　預測、研究、企業。

## 三、衝突與矛盾
