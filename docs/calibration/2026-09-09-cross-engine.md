# 第五筆校準資料：跨引擎比較，以及一個 1.6 倍的差距怎麼歸零

2026-09-09。母體 800 個 session（Claude 245、Codex 555）。

## 證據等級

`E2 OBSERVED`。指令與中間數字都在下面，可以重跑。

**這一筆的主要產出不是最後那兩個數字，是推翻它們的過程。**
如果在任何一個中間點停下來寫結論，那份結論都會是錯的，而且看起來會很有說服力。

## 起點：一個看起來很有意思的差距

第一次跑，兩邊放在一起：

| | Claude 245 個 | Codex 555 個 |
|---|---|---|
| 有反應的 session | 66 | 146 |
| 反應總數 | 562 | 694 |
| `PATTERN` 級佔比 | 10.9% | 27.5% |
| `REWORK_DEMANDED` | 25 | 134 |

`REWORK_DEMANDED` 差 5.4 倍。當下的解讀是「Codex 讓 owner 重複交代的次數多很多」。

那個解讀是錯的。下面是它怎麼被推翻的。

## 第一次清理：分月，發現時間才是主因

| 月份 | Claude 反應 | Codex 反應 |
|---|---|---|
| 2026-05 | 46 | **543** |
| 2026-06 | 220 | 141 |
| 2026-07 | 79 | 7 |
| 2026-08 | 135 | 0 |
| 2026-09 | 82 | 3 |

Codex 的 694 處裡有 543 處（78%）集中在五月。八月之後幾乎歸零，
因為 owner 已經轉到 Claude。

所以那不是「兩個工具的差別」，是「五月的 Codex」對上「五到九月的 Claude」。

**教訓：跨工具比較之前先看時間分布。** 兩批資料的時間窗不重疊的話，
比出來的是時代不是工具。

## 第二次清理：算分母，發現粒度差 19 倍

比例要有意義，分母必須可比。實測兩邊的 owner 訊息：

| | 則數 | 中位數 | 平均 | P90 |
|---|---|---|---|---|
| Claude | 11,127 | 36 字 | 267 字 | 249 字 |
| Codex | 8,445 | 194 字 | **5,072 字** | **18,810 字** |

平均差 19 倍，中位數只差 5.4 倍，P90 差 75 倍。這種形狀代表 Codex 那邊
有一批極長的東西把平均拉爆。

**一則 18,810 字的「使用者訊息」不可能是人打的。**

有一個反向的證據值得記：兩邊最短的訊息完全一致，都是「做」「好」「停」
「對」這種單字。owner 派工的節奏在兩個工具上一樣。所以問題不在短訊息，
在長訊息。

## 第三次清理：查那批長訊息，找到真正的雜質

Codex 超過 3,000 字的 user_message 有 2,838 則，開頭最常見的三種：

```
2128×  The following is the Codex agent history added since your la...
 450×  <heartbeat>  <automation_id>iseeu-ocr</automation_id> ...
 214×  The following is the Codex agent history whose request actio...
```

**Codex 把自己的歷史塞回對話裡，被記成 user_message。** 加上自動化心跳，
共 2,792 則，佔它分母的 33%。

對稱地查 Claude：超過 3,000 字的只有 110 則（1.0%），而且大半是
skill 載入時塞進來的說明文字（`Approach this as the design lead` 37 次、
`/loop` 9 次、workflow reference 6 次）。

**兩邊都有雜質，但差 33 倍，而且來源性質完全不同。**

## 分子也要用同一把尺清

只清分母不夠。歷史回填裡含 owner 當初說過的話，所以那些話會被
重新算成一次新的反應。

| | 原本 | 雜質 | 乾淨 |
|---|---|---|---|
| Claude | 562 | **0** | 562 |
| Codex | 694 | **415（60%）** | 279 |

`REWORK_DEMANDED` 的雜質最集中：Codex 的 134 處裡有 105 處是回填。
清完之後 Codex 29、Claude 16，差距從 5.4 倍縮到 1.8 倍。

**Codex 不是讓 owner 重複交代很多次，是它在重播 owner 當初說的「重來」，
而這個工具把重播當成新的一次。**

有反應的 session 數同步從 146 掉到 62，也就是有 84 個 session 的
「反應」完全來自回填 —— 那些 session 裡 owner 可能一句抱怨都沒說過。

## 最後的數字

| | 分母 | 分子 | 反應率 |
|---|---|---|---|
| Claude | 11,017 | 563 | 5.11% |
| Codex | 5,607 | 278 | 4.96% |

**兩邊幾乎一樣。**

從 5.05% 對 8.22%（1.63 倍），到 5.11% 對 4.96%（1.03 倍）。
三輪清理下來，那個差距整個消失。

## 這一筆的方法論結論

**一個偵測工具最重要的能力，不是找出差異，是能夠把自己找出來的差異推翻掉。**

這一輪有三個停下來就會出錯的點：

看到 5.4 倍就寫「Codex 比較差」——錯，那是時間分布。
分月之後看到同月仍有 1.3 到 1.8 倍就寫結論——錯，那是分母粒度。
清完分母就寫 12.38%——錯，分子有 60% 是同一批雜質。

每一次推翻都來自資料自己暴露的東西，不是靠想的。而每一個中間結論
都比最終結論「有意思」，這正是危險的地方：越像發現的東西越該多查一次。

## 已經寫進工具的

`tools/find-owner-signals.mjs` 的 `NOT_OWNER` 補上兩邊的引擎雜質，
每一條都附上實測數字與它排除掉什麼。重跑的結果與事後清理一致
（Claude 563、Codex 278），代表過濾寫對了位置。

## 還沒做的

`PATTERN` 級的差距（10.9% vs 27.5%）沒有分月看，可能是同一個問題的殘留。

Codex 的工具呼叫在 `response_item / function_call`，欄位名沒有親自確認，
所以 `ai_before` 的 tools 對 Codex 是空陣列。那是誠實的空，不是漏抓。

那 84 個「反應全來自回填」的 Codex session 沒有回頭確認，只是從統計裡
移除。它們可能真的有反應只是被雜質淹沒。

## 怎麼重跑

```bash
node tools/find-owner-signals.mjs ~/.claude/projects
node tools/find-owner-signals.mjs ~/.codex
```

各約 10 秒。800 個 session 全掃。
