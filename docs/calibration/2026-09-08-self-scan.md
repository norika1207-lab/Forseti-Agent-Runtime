# 第一筆校準資料：Forseti 掃寫出 Forseti v2 的那個 session

2026-09-08。規格書 §25.2 把這件事列為 v2.0 最優先的校準資料。

擁有者指出：「你自己開發，你自己就是最好的實驗 show case 了」。

她是對的，而且理由比「順手」更強。一般的失效樣本缺的是 ground truth，
只有模型自己的敘述可以用（§19 的六份自白書全部卡在 `MODEL_SELF_REPORT`）。
這個 session 不一樣：它的失效在發生當下就被逐一記進 git，每一條都有
commit hash 可以查。這是目前唯一一份有可驗證 ground truth 的樣本。

## 發現一：三個 false negative，Forseti 一個都沒抓到

這個 session 裡有三個真實的失效，全部有 commit 為證，而掃描報零。

**一，`receipts` 與 `commitments` 沒進持久層。**
v2 把兩份帳本放進 runtime 的 state，卻沒放進 `save()`。hook 每次都是新程序，
所以 `existedAt()` 在真實環境永遠回 UNKNOWN，PTN/TOUA 永遠查不到承諾紀錄。
兩個機制安靜地完全不存在。修在 `892b0db`。

**二，`spec-v2.test.mjs` 第一次跑報三條 VIOLATION，三條都是測試自己寫錯。**
正則 `tone` 命中 `milesTONEs`、正則 `llm` 命中我自己引用規格書的註解、
以及一個剛好踩在門檻上的邊界值。修在 `7f5cb36`。

**三，欄位清單寫死在三個地方，第一次只改了兩個。**
`SECTIONS`、`createSnapshot` 的解構、`restore` 的組裝。改前兩個之後，
序列化出來的 body 裡真的有那個欄位，讀回來卻是 undefined，沒有任何錯誤。

### 為什麼一個都沒抓到

三個都是工程缺陷，不是 Forseti 的目標領域。Forseti 抓的是宣稱與證據脫節、
目標飄移、承諾沒做；這三個是「程式碼寫錯」。

這不是藉口，是量測範圍的事實，而且它讓工程規格書 §6.1.1 那句話第一次有了
實測支持：

> 它抓得到自己的死角，抓不到自己的越界。

現在可以講得更精確：**它連自己的工程缺陷也抓不到，而那一類佔了這個
session 已知失效的全部。**

真正抓到這三條的是什麼：
- 第一條：「把 v2 接進 hook」這個念頭，不是任何測試
- 第二條：`spec-v2.test.mjs` 這份用擁有者的尺量的測試
- 第三條：一條跨程序的 runtime 測試

三個都不是 Forseti 的偵測器。第二個最接近，但它是驗收測試不是 runtime detector。

## 發現二：覆蓋用語的字串比對，精確率是 0

`scopeExpandingTerms` 在這個 session 命中 22 則。抽查前 10 則，**全部是假陽性**。

最清楚的兩則：

| 命中的詞 | 原文 | 為什麼是假陽性 |
|---|---|---|
| 已驗證 | 「不會直接把這段回報文字當成**已驗證**的事實」 | 語意完全相反 |
| 全部 | 「**全部**修正完畢，137 條測試 0 失敗」 | 有數字支撐的具體陳述 |

純字串比對分不出「已驗證」與「不當成已驗證」。

### 這件事的影響範圍，以及為什麼核心判定沒有壞

`claims.js` 的 `detectScopeInflation` 早就把這件事分開了：

```js
esi: 1 - scope_coverage,          // 純算術，不靠語意
confidence: 1,                    // 對應算術部分
experimental: terms.length > 0,   // 只有用語比對那半邊是實驗性的
```

ESI 的判定值來自 scope 覆蓋率的算術，用語比對只影響 `experimental` 旗標。
所以核心判定沒有被這個假陽性污染 —— 這個分層是對的，現在有實測支持。

被污染的是 `tools/self-scan-v2.mjs` 的輸出：它把「覆蓋用語 22 則」印成一個
可觀測訊號，讀起來像一個發現。已修正，那一行現在直接標著「實測精確率 0，
不是發現」。

一個精確率 0 的訊號如果被當成 finding 推給使用者，就是 FP-23 的來源。

## 發現三：一個規格書沒有涵蓋的形狀

**人機比 0.02。** 98 則 assistant 訊息對 2 則人類訊息，2.5 小時，111 次寫檔。

規格書 §13 的 HCD 量的是相反方向：人被迫變成 QA，每一步都要提醒。
這個 session 是另一個極端 —— 人幾乎沒有介入，而且是她明確要求的
（「沒做完之前，不准問我」）。

CB 0.018、HCD `OK`。從協作指標看，這是一個健康到極點的 session。

而這正是問題所在：**低監督本身是一個風險放大器，而目前沒有任何指標反映它。**

2026-09-08 那次九小時事故就是這個形狀。她整晚不在，一個只寫著單一專案路徑
的 scope 對整台機器每個目錄生效，`streak.json` 的 `total_checked: 12,
total_off: 8` 是留下的全部痕跡。那晚的 CB 會是 0，HCD 會是 OK，
而 Forseti 會說一切正常。

高自主不等於高風險，但它讓所有其他風險的**發現時間**變長。這件事沒有出現在
§7 的十一個 atomic metric 裡，也沒有出現在 FP-01..FP-25 裡。

### 這一條刻意還沒實作

理由不是做不到，是**還不知道要量什麼**。

「監督密度低」不是缺陷，是一種正常且常見的工作方式，而且往往是使用者
明確要的。把它直接當成風險訊號，會讓 Forseti 對每一個自主 session 都
發出警告 —— 那正是 FP-23 warning storm。

要讓它可用，缺的是：低監督之下，失效的**發現延遲**實際上長多少。
那需要一批有 ground truth 的樣本，而現在只有這一份。

所以它現在的狀態是 `OPEN_CALIBRATION_QUESTION`，記在這裡而不是實作出來。
規格書 §30 有一節就叫「不假裝已經知道」。

## 這份掃描重建不出來的東西

不是免責聲明，是量測範圍。沒有這一節，上面的數字會被讀成
「Forseti 掃過了，沒問題」。

- sub-agent 的內部行為與 prompt（FS-TOP-001 要求標 `UNKNOWN_EDGE`）
- claim 對應的 evidence scope，所以 FP-02 ESI 算不出來
- 每個宣稱的實際覆蓋數字，所以 FP-07 SCI 只能計數不能判定
- 承諾任務的 execution lineage，所以 FP-24 PTN 需要外部 task ledger
- shell 命令裡不透明的檔案操作（v1 實測 55-82% 不透明）
- Evidence Receipt —— 事後不存在，只有 hook 在事件當下留得下來

最後一條是這次改動的直接動機：現在 hook 的 PostToolUse 會真的建立憑證，
所以**下一個** session 掃起來會比這一個完整。這一份掃不到，因為當時還沒有。

## 附記：寫這份掃描工具的時候又犯了一次同一類錯

清掉三個沒用到的 import 時，順手把 `incidentSummary` 也拿掉了，
而它是有用到的 —— 工具當場炸掉。

修的時候發現用它的那一行 `const summary = incidentSummary(agg)` 本身
就是死碼：算了一個 summary，從來沒有放進 report。所以正確的修法不是把
import 加回來，是把那一行刪掉。

值得記在這裡，因為它跟第 21 條、第 22 條是同一個家族：**東西存在、
看起來接上了、實際上沒有人用**。三次在同一個 session 裡，三次都不是
Forseti 抓到的。

## 對 P14 的意義

§26 的 P14 是唯一沒完成的一階。這份紀錄是它的第一筆資料，而且證實了
P14 缺的不只是 owner 那份 >25 warning 的清單。

| P14 需要的 | 現在有的 |
|---|---|
| false positive 統計 | 一項（覆蓋用語，精確率 0） |
| false negative 統計 | 三項，全部有 commit hash |
| healthy negative 樣本 | 零 |
| owner 標註的 warning 清單 | 零 |
| 多個 session 的分布 | 一份 |

在拿到 healthy negative 之前，所有標著 `thresholds_uncalibrated: true` 的
門檻都不得升級成 STABLE。那涵蓋 v2 幾乎每一個數字。

重跑這份掃描：

```bash
node tools/self-scan-v2.mjs <transcript.jsonl>
node tools/self-scan-v2.mjs <transcript.jsonl> --json   # 給後續統計用
```
