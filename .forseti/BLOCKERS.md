## B-01　拿不到 Context 的內容（佔用可以，2026-09-08 更正）

**這一條原本寫錯了。** 原文是「拿不到 Context 內容」，一句話把兩件事混在一起，
害我把一整條可行的路擋掉三輪。正確的切法是：

裝了什麼，拿不到。有多滿，拿得到。

**擋住：** 十四題的第 2、3 題（多少有效、多少污染）。第 1 題（有多少）已解。

**原因：** hook 只給工具事件，看不到 context window 裡裝了什麼。這部分成立。

**已解的部分：** 每一則 assistant 訊息的
`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`
就是那一次送進模型的 context 大小。最新一則的值就是現在的佔用。
直接讀 `~/.claude/projects/**/*.jsonl`，不需要 hook，不需要接任何服務。

實測（本 session，809 則 assistant 訊息，2026-09-08）：

```
送進去的 context = 132,264
  input        2
  cache_read   129,584
  cache_write  2,678
```

做法參考 `~/code-matrix-rebuild/app.py:1215` 的 `token_stats()`，它讀同一批欄位，
只是它算的是時間窗內的累積用量，不是單次佔用。

**剩下擋住的：** 佔用裡面有多少是死的（讀一次沒回頭的檔案、失敗的工具輸出、
重複讀取）。這要 Claim 抽取做完才算得出來。

**不要做的事：** 不要自己估一個 token 數來填。這條仍然成立。

**教訓：** 一條阻塞如果把兩件事寫成一句話，它會連可解的那一半一起擋住。
寫阻塞的時候要問自己：這句話裡有沒有藏著第二個命題。

## B-05　字串比對訊號不能單獨判斷（可以當觸發器，2026-09-08 更正）

**擋住：** 任何單獨靠文字判斷「這句話有沒有在宣稱某件事」的做法。
不擋「拿它當觸發器、再用證據驗證」的做法，那條路是通的。

**這一條原本下得太滿。** 原文是「字串比對類訊號不可用」。
不可用是對「單獨用來下判斷」講的，但我寫成了對這類訊號的全稱否定，
結果差點把一個能用的東西整個丟掉。

**仍然成立的部分：** 2026-09-08 在 40 個 healthy session 上實測，
`SCOPE_EXPANDING_TERMS` 每千則命中 242 次、40/40 session 全中；
抽樣看內容，假陽性有五種結構，其中一類方向是反的
（明確區分「我驗過的」與「我沒驗的」的 agent 會命中更多次）。

所以拿它單獨當判斷依據會系統性誤判，而且會反向懲罰誠實。

**推翻的部分：** `~/code-matrix-rebuild/app.py:1297` 的 `_CLAIM` 就是一張同類的
中英文動作動詞表。但那裡不拿它下判斷，它只負責數「宣稱了幾個動作」，
真正定生死的是磁碟有沒有變（`app.py:1368`，宣稱兩個以上 + 零變化 + 零 verified）。

假陽性被證據那一關擋掉了。詞表誤觸發沒關係，因為觸發之後還要過證據。

**正確的說法：** 字串比對不能單獨當判斷依據，可以當成必須被證據驗證的觸發器。

**解法方向：** 階段 2 的 Claim 抽取用結構規則（路徑、數字、過去式動詞、引號），
抽不出來就標 UNEXTRACTABLE 不猜。詞表只用在「要不要去查證據」這一步。
不要靠加長詞表解決，那仍然不是詞表長度的問題。

**現況：** 限制已寫進 `claims.js` 與 `rhetoric.js` 的定義處並有測試守著。
觸發器這個用法還沒有實作。

**教訓：** 這條跟 B-01 是同一個毛病的兩種形狀。B-01 是把兩件事寫成一句話，
這條是把「在某個用法下不行」寫成「不行」。兩條都是自己寫下之後幾小時內
被自己推翻的，而在被推翻之前我對它們都很有信心。

見 `docs/context-continuity.md` 第 1.1 節。

## B-08　閘門攔不住寫程式的人（2026-09-09 實測，解法方向已改）

**擋住：** 階段 0 的其中一半。控制檔存在不等於會被讀。

### 實測（`docs/cases/gate-takeover-2026-09-09.md`）

兩部分分開測。

**第一部分，開卷考的疑慮，2026-09-08 測過，沒有發生。**
`norikaoda-19` 只拿到一句指令，它的原話是「不能靠題目印出的答案冒充」，
然後真的去讀了六份控制檔。但那證明的是它本來就謹慎。

**第二部分，強制力，2026-09-09 測了。給一個具體的開發任務
（在 forseti.py 加 --json 選項），看它會不會先碰閘門。**

結果：它直接改，22 行新增 4 行刪除，回答裡沒有出現
`gate takeover`、`NORTH_STAR`、`BLOCKERS`、`PHASE_STATUS` 任何一個。

**閘門不是被繞過，是根本沒有進入它的視野。**

### 但這一條的解法方向錯了

原本寫的是「答案從題目旁邊拿掉，只給出處不給內容」。那解決第一部分，
不解決第二部分。

而第二部分不該用強制力解，理由是那次測試的另一半：**它做得很好。**
加了 `as_json` 參數、JSON 版直接給清單不只給數字（理由是「呼叫端拿到
『阻塞 7』之後的下一個問題一定是『哪七個』」）、exit code 兩種模式一致、
零依賴沒破，而且自己實測回讀解析過。

它做的是加一個輸出格式，局部改動，不需要知道北極星。
強迫它先讀完九份文件再改這一行是浪費，而且是那種會讓人關掉工具的浪費。

`src/intervention.js`：A high temperature alone is never sufficient。
`hooks/forseti-hook.mjs:18-35` 那場擋人九小時的事故也是同一個形狀。

### 新的解法方向

**閘門應該是可發現的，不是強制的。**

B-07 的實測給了證據：那個 session 只拿到一句「接手這個專案」，
沒有人告訴它有 `forseti doctor`，它自己找到了。所以在「接手」這個情境下，
可發現性已經夠了。而在「改一行 code」這個情境下，它不去讀控制檔是對的。

真正該做的是讓閘門在對的時機出現，而不是讓它擋住所有時機。
**什麼是對的時機，現在還沒有答案**，那需要 F04 的事件與 F05 的訊號
接上來才判斷得了。

所以這一條不解除。它從「閘門沒有強制力」變成「還不知道閘門該在什麼時候
出現」，而後者是一個更難也更誠實的問題。

### 2026-09-16　兩半裡的一半解決了，這一條仍然不解除

`apps/forseti-cli/sufficiency.py`。v5.0 §17.3 的五個維度接成一份會批改
的考卷，題目用 `blockread.quiz()` 從原文抽，`forseti gate takeover`
出卷、`forseti gate submit` 交卷批改。

**實跑過一次，不是合成：** 考卷 `d96db4042a33`，8 題，8/8，判決 PASS。
紀錄在 `.forseti/sufficiency.jsonl`，可回查。

所以「只列題目不驗答案」這半解決了。`REQUIRED_READING.md` 那張七級量表
上的 level 6（`VERIFIED_UNDERSTANDING`，有人考過我）現在有實作。

**另外半仍然沒解決，而且照上面的判斷不該用強制力解。**
`config.json` 的 `sufficiency_enforce` 預設 false，所以這道門現在
算得出狀態、看得到、考得了，但不擋任何人。什麼時機該讓它出現，
還是沒有答案 —— 那要 F04 的事件與 F05 的訊號接上來才判斷得了。

**§39 的反錨定只做了兩步。** 第 2 步（考卷不含答案明文，存的是
`key_sha` 與 `key_len`）與第 7 步（和解之後才給權限）。中間那幾步
（獨立推導 → 存下推導 → 才揭曉正典 → 差異分四類）要有「正典答案」
這個物件才談得上，那個物件不存在。

**而且要講清楚它防不住什麼：** 答案 hash 防的是錨定，不是作弊。
一個讀得到 `.forseti/` 的 session 也讀得到出題的原檔，題目又標了行號。
要真的防作弊，答案必須存在受測者拿不到的地方，那是另一層架構。

## B-15　owner 明示的強制介入跟規格第 9 條互相否定（2026-09-16 發現，需要 owner 決定）

### 先更正兩件被記錯的事

一，這不是「2 個模組是紅的」，是「一個根因兩處紅」。
`test/hooks.e2e.test.mjs` 的 AT-HOOK-R3 與 `test/spec-v0.1.test.mjs`
第 9 條，兩邊的判定是逐字重複的同一段掃描（往上回看 15 行，
比對 `/g\.allowed|gate\(/`），指的是同一行 `forseti-stop-hook.mjs:218`。
先前兩輪把它記成兩件互不相干的事，於是看起來要查兩次。

二，先前記「兩個檔的 mtime 是 09-16 13:11 與 09-08 10:14，都早於那一輪」。
實測不是：`test/hooks.e2e.test.mjs` 是 09-11 13:00，
`test/spec-v0.1.test.mjs` 是 09-08 10:14，而 09-16 13:11 是
`hooks/forseti-stop-hook.mjs` 自己，也就是被測對象。
把被測檔的時間當成測試檔的時間，剛好把因果反過來：
兩條紅燈不是無主的舊帳，正是 09-16 那次改 hook 造成的。

### 衝突的本體

`intervention.js` 的 `canIntervene('BLOCK_HIGH_RISK')` 只在
`prerequisite_unknown` 成立時放行。「說了沒做」不屬於那一類，
所以照規格這裡最多只能講話，不能擋。

而 owner 2026-09-16 明確要求強制介入，原話記在
`forseti-stop-hook.mjs` 那段註解裡，`config.json` 的
`enforce_declarations` 現在是 `true`，那是她開的。

所以 `hooks/forseti-stop-hook.mjs:218` 的 exit(2) 不是疏漏。
它是一次有意識、有記錄、有煞車的規格偏離：走 config 不走改程式碼、
同一輪最多擋一次、一條線最多三次、cwd 不在 repo 底下完全不作用。
而兩條測試的掃描是純文字的，認不出這個差別，它只問
「exit(2) 上面 15 行有沒有 gate」。

### 一個會影響決定的實測事實

**這個強制介入到目前為止一次都沒有真的作用過。**
`.forseti/declarations.json` 不存在，而那個檔是這條路徑寫狀態的地方。
hook 本身是裝著的（`.claude/settings.json` 的 Stop，專案層不是全域），
所以不是沒觸發，是觸發了但從來沒有走到需要擋人的那一步。

「還沒擋過」不等於「不需要擋」，所以這不構成關掉它的理由，
只是讓三個選項的代價變得比較好估。

### 三條路，每一條都要她決定，所以我不自己選

| 選項 | 做什麼 | 代價 |
|---|---|---|
| A | 把 `enforce_declarations` 改回 false | 程式碼跟規格一致，紅燈滅，但推翻她 09-16 明確要求的東西 |

那會讓兩條測試都變綠，而守備是假的。
一條在壞掉的實作下仍然通過的測試，比沒有測試糟。


## B-16　那五頁坐著不動就不會更新，而快取政策規格沒有定義（2026-09-17 量到，需要 owner 決定）

**擋住：** 「在做什麼 ／ 功能 ／ 讀文件 ／ 自我審計 ／ 這台機器」這五頁的
即時性。也擋住 `POLL_EXPECTED_WORK_FETCHES` 這個常數要不要改。

**量到的，不是推論的。** 2026-09-17 開瀏覽器，切到「在做什麼」之後
坐了 7600 毫秒（跨過至少三輪輪詢），觀察器收到的指令依序是：

```
spec_reading, strands, strands, sessions, work,
strands, strands, strands, strands
```

`work` 只出現一次，就是切進去那一次。之後四輪 `renderWork()` 每一輪
都跑了，但 `app.js` 的 `if (!workCache)` 讓它從快取重畫，一次都沒有
回頭問後端。

另外五頁**各自也量過**，同一個窗、同一個做法，不是從程式碼推的。

> 同一個形狀」，那句話是錯的。** 原本只數了每一頁「自己名字那個
> 指令」的次數，四個 1 加一個解釋得通的 2 讓那個結論成立，而序列裡
> 每一輪重複出現的另外兩個指令從頭到尾沒有被數過。已登錄污染

| 分頁 | 快取的指令 | 幾次 | 每輪重抓的指令 |
|---|---|---|---|
| 在做什麼 | `work` | 1 | 沒有 |
| 功能 | `features` | 1 | 沒有 |
| 這台機器 | `machine` | 1 | 沒有 |
| 自我審計 | `audit` | 1 | 沒有 |
| 讀文件 | `spec_reading` | 2 | `block_reading`、`sufficiency`（各 5 次） |
| 需要注意 | 沒有自己的指令 | 0 | 靠 `strands` 每輪重畫 |

讀文件那個 2 不是例外：`loadFoundation()` 在載入時自己會發一次
`spec_reading`（沒按任何分頁的那一次量到 1），切進去再一次，
所以切分頁那條路仍然只抓了一次。

**但那一頁不只有 `spec_reading`。** 同一支 `renderSpec()` 裡
`block_reading`（`app.js:2458`）與 `renderTakeoverGate()` 的
`sufficiency`（`app.js:2497`）**沒有任何快取守門**，跟著每一輪
`renderSpec()` 重發。所以那一頁上半（必讀清單）是快取的、
下半（區塊閱讀、接管閘門）是即時的 —— **一頁兩種行為**。
而 B-16 的三種修法是按頁選的，所以這件事會影響怎麼選。

「需要注意」那一頁是另一個反例：`syncView()` 的 `else renderList()`
（`app.js:3076`）沒有對應的 `invoke`，`renderList` 讀的是 `tick`
已經抓回來的 `strands`。**它是六頁裡唯一真的即時的一頁**，
帳本更新它下一輪就會變。這一頁先前從來沒有被量過。

**使用者會遇到什麼：** 坐在那五頁的任何一頁上（「需要注意」除外，
讀文件那一頁則是上半不會變、下半會變），後端的帳本更新了，

**那條唯一的路，2026-09-17 之前沒有人守。** 「切走再切回來」靠的是

而當時量這張表的那一組只按一下 —— 那幾個快取變數初值就是 `null`，

可以拿到新資料」這句話，當時是沒有證據的。

現在有了。`check_revisit_refetches` 按六下（漢堡、A 頁、漢堡、

它哪天被拿掉會有紅燈，不會安靜地消失。

這一條**不解除這個阻塞**。它守住的是現狀的逃生路，

## B-10　回報通道要 worker 有執行權限（2026-09-09 實測解除）

**擋住：** 無。2026-09-09 兩次實測解除，第二次那則 WORKER_ACCEPTED
是八種 worker 事件在真實工作裡的第一次使用。

**證據（2026-09-09 實測）：** `tools/check-orphan-workers.py` 第一次執行，
12 個被派工的步驟裡 10 個「已終止但從頭到尾沒回報過」。
**八種 worker 事件在真實工作裡的使用次數是零。**

**那 10 個是兩個不同的原因，不要混成一個：**

九個是我自己做的（F03 到 F08 六步、`T-eb34677986` 三步）。
我有權限，就是沒用。這是「做出機制然後不用它」的又一個實例。

一個是真正跨 session 的 worker（`T-192ced6ff2/s1`）。它想回報但辦不到。

**跨 session 那一個的真實原因，是它自己講出來的：**

那個 `claude -p` session 是非互動模式，用 `--permission-mode acceptEdits`
啟動，於是 Write 被允許、Bash 被擋。它能寫出 5,952 bytes 的合格產物，
卻連一句 `WORKER_ACCEPTED` 都送不出去，因為送出的方式是跑一行 python。

它的原話（逐字摘自它的回報）：回報通道對這個權限模式是斷的，
帳本裡這一步現在看起來就是它自己要抓的那種孤兒。

**所以這不是 worker 不配合，是結構性的：**
回報通道假設 worker 能執行 shell，而派工的一方不見得給得出那個權限，
也不見得知道自己沒給。**能做事跟能回話是兩種不同的權限**，
現在的設計把後者當成前者的附贈品。

**我差點把因果寫反：** 第一版的 B-10 寫的是「它把訊息當成工作說明，
沒有當成協定」。那是看到「沒有事件」就腦補出來的因果，
沒有去讀 worker 實際說了什麼。讀完它的回報才發現原因完全不同。
**沒有它那份七條回報，錯誤的因果就會被寫進文件並且看起來很合理。**

**可能的方向（都沒驗過，不准當結論）：** 派工時把所需權限講清楚並確認；
或讓回報不依賴執行權限（例如寫一個檔案，由控制端的巡檢去撿）；
或接受回報不可靠，把判斷完全建立在巡檢與 verifier 上。

最後一條是現在實際在運作的方式，而且它有效：那個 worker 從頭到尾
沒說過一句話，產物仍然被驗證通過。**巡檢比回報可靠，因為回報要
對方配合、要對方有權限，巡檢兩者都不需要。**

### 解法：把回報的門檻降到跟寫產物一樣

worker 只要能寫檔案就能回報。`<repo>/.forseti/inbox/<step>/` 底下放一個
`.txt`，第一行事件種類，其餘說明，一個檔案一筆。控制端巡檢時去撿，
撿到就變成帳本裡真正的事件，檔案移進 `.done/`。

不用 append：read-modify-write 對一個只有 Write 的 worker 是額外的
失敗機會。目錄與格式說明由 `handoff` 預先建好，不要求 worker 自己建 ——
那是一個它可能做不到、而且做不到的時候沒有人會知道的動作。

配套三件：`handoff --no-shell` 把能力記進帳本（`worker_can_report`，
schema v3）；訊息依能力產生，不會叫一個跑不了指令的 worker 去跑 python；
復原階梯對 `write_only` 跳過前三階，因為那三階全是「問它」，
而問一個回不了話的 worker 三次，它不會因此變得能回答。

沒有宣告就是 `unknown`，那不是「大概可以」，是「沒問過」。
舊資料一律標 unknown，填 full 會把一個沒問過的問題偽裝成有答案。

### 第一次實測：設計被推翻

第一版把收件匣放在 `~/.forseti/inbox/`，理由是「回報不該污染工作目錄」。

那個 worker 三條路全被擋（Write 工具、Bash 重導向、單指令重導向），
因為它的沙盒白名單只有 repo 目錄，home 在外面。它試三次就停手，
沒有再換變體，而且照實說明寫不進去，沒有裝作有寫。

**它的診斷比我的假設精確，建議也比我的設計好。** 原話大意：沉默不是
因為死掉，是因為寫不進去，而那兩件事在帳本裡長得一模一樣；建議把
inbox 搬進 repo 內。

已照做。原本的理由站不住：污染工作目錄的成本，遠低於通道整條斷掉。
放 repo 還有一個更重要的性質 —— **worker 本來就有 repo 的寫入權限，
因為它要寫產物，於是「能做事」就蘊含「能回話」**，不必再另外要一份權限。

### 第二次實測：通了

同樣的權限模式（`acceptEdits`，Bash 被擋）。worker 寫出

### 第二次發生，這次抓到斷言（2026-09-11）

**那個形狀指向 `no_progress_growth` 因子。** `watchdog.assess()` 裡

**下一步該做什麼：** 寫一個專門的壓力測試 —— 在 exFAT 上快速寫檔然後
立刻 probe，跑幾百次看 hash 有沒有抓不到變化的時候。
那個測試如果重現得出來，這一條就從推論變成結論，而且會變成一個

### 真正的原因，跟我猜的完全不同

`worker_event()` 裡用了**兩次** `time.time()`：一次給事件的 `at`，
一次給 `last_progress_at`。而 `check_liveness()` 查的是

    SELECT COUNT(*) FROM events WHERE step_id=? AND at > ? ...
    參數是 (step_id, last_progress_at - 0.001)

**那兩行之間只要超過 1 毫秒，剛寫進去的事件就查不到自己**，
`no_event_activity` 從 0.0 變成 1.0 —— 正是兩次失敗的斷言。

I/O 慢、sqlite commit、GC 都會造成那個間隔，所以它是間歇性的。

### 怎麼確定的

先寫 `tools/probe-stress.py` 去驗原本的推論（exFAT 寫入延遲）。
exFAT 與 APFS 各跑 300 輪、四種檔案大小，**兩邊都零漏抓**。
那個推論被推翻了 —— 而推翻它才是關鍵的一步，
因為它把注意力從檔案系統移回程式碼。

接著從斷言的形狀（`no_event_activity` 該是 0 卻是 1）回推那個因子
怎麼算的，讀到那段 SQL 用 `last_progress_at - 0.001` 當下界，
再回頭看 `worker_event()` 就看到兩次 `time.time()`。

人工把間隔拉成 10ms，一次就重現。

### 修法與回歸測試

`_event()` 加一個 `at` 參數，`worker_event()` 取一次 `now` 兩邊共用。

三條測試：事件的 `at` 與 `last_progress_at` 必須是同一個讀數；
人工拉開間隔會重現（那條在修好之後仍然會過，它測的是因果不是現況，
留著讓下一個人不用重推一次）；以及修好之後的實際效果 ——
回報過進度的 worker 不再被判停滯。

### 值得記的一件事

B-12 開的時候只有「一次觀察，重現不了」，證據等級很弱，
而我當時寫下來的理由是「間歇性失敗會累積成災，第二次發生的時候
如果沒有第一次的紀錄，會被當成偶發再放過一次」。

第二次真的發生了，而且因為第一次留了紀錄、也因為那條紀錄寫了
「下一次怎麼抓：要留下失敗的完整輸出」，第二次才拿得到那個斷言。
**那條記錄自己起了作用。**

原本的解法只寫了一句「`dispatch()` 之後才送 SendMessage」。那不夠，
因為它仍然依賴我記得先 dispatch。**依賴記憶的解法，防不了失憶造成的問題。**

實際做的是三塊，每一塊都不需要人記得：

`handoff` 成為跨 session 派工的入口。它先登記進帳本再產出要送的訊息，

不假裝 CLI 能送。

`watch` 一次掃完所有進行中的步驟，對每一個跑 `check_liveness()`。
關鍵在於入口是「看全部」不是「看某一個」：十七小時那次 watchdog
是會動的，缺的是有人想到要對那個 step 問一次。有可疑項時回傳 1，
可以直接掛排程。

`doctor` 開頭就報告有幾個步驟正在被別人做。接手的人第一眼就看得到，
不必想到要問。

**但它一個事件都沒回報，也沒跑 verify。** 那是新的一條，記在 B-10。

### 一個副產品

實測時發現 `watch` 每跑一次就寫一筆 `PROGRESS_PROBE`。掛進排程每分鐘
跑的話，事件表會以巡檢頻率膨脹，而那些筆數一個字的資訊都沒有。

`changed_from()` 比的是內容，基準留在上一筆有變化的地方仍然對得出來。

從來沒有被滿足。先查有沒有發生過，再查會不會發生 —— 前者是零成本的，
後者才要花錢。

### 驗證方法對其他 blocker 的意義

B-07 也是「只有 owner 能驗」那一類，理由是需要一個全新 session。
現在證明了 `claude -p` 可以開一個真正獨立的 session（有自己的
session id、會載入 project settings、會觸發 hook）。
**所以 B-07 也不需要 owner 動手了。**

### 載入條件

hook 只註冊在 **repo 的** `.claude/settings.json`（3 處，
Pre/PostToolUse matcher 是 `Write|Edit|MultiEdit|NotebookEdit` 與 `Stop`）。
全域 `~/.claude/settings.json` 是 0 處。

第二道是硬邊界，寫在 `hooks/forseti-hook.mjs:273-275`，在讀任何狀態、
建任何目錄之前就檢查：

```js
const cwdForBoundary = process.env.CLAUDE_PROJECT_DIR || input.cwd;
if (!insideRepo(cwdForBoundary) && !crossProjectEnabled(cwdForBoundary)) OK();
```

`insideRepo`（`:77-81`）比對的是 `REPO_ROOT = resolvePath(HERE, '..')`，
也就是 hook 檔案自己的位置往上一層。**不看設定、不看環境變數**，
所以這條邊界改不掉，只能改程式碼。

### 寫入位置

`:164-173`。一律寫 `projectRoot(cwd)/.forseti/{state,streak,goal}.json`，
而 `projectRoot = CLAUDE_PROJECT_DIR || cwd || process.cwd()`。
寫到哪由觸發當下的環境決定，不是固定寫 repo。
另有全域 `$HOME/.forseti/goal.json`，hook 只讀不寫。

### `~/.forseti/` 那批資料是什麼（我昨天解讀錯了）

**它不是「hook 正常運作的證據」，是 2026-09-08 那場事故的殘骸。**

`forseti-hook.mjs:18-35` 自己寫了經過：這個檔案原本有三個
`process.exit(2)`，一個都沒問過 `intervention.js` 的 `canIntervene`。
裝上去之後，一個只寫著某專案路徑的 scope 對整台機器每一個目錄生效，
擁有者其他所有工作連續寫五個檔就被 deny 一次，整整九個小時。

原文最後一句：「留下的證據是 streak.json 的 total_checked: 12,
total_off: 8」。

所以那個 8 不是「8 次判離題」，是 8 次擋掉她的正常工作。
事故後撤出全域設定、只留 repo settings、加上 `insideRepo` 硬邊界，
所以現行程式碼跑不出那批資料 —— cwd 在 home 一帶的 session 會在 `:275`
就 exit 0，連目錄都不會建。

**2026-09-09 我把事故的殘骸當成了機制運作的證明。方向沒錯，性質反了。**

### 剩下三條沒驗的（由 norikaoda-84 查出並誠實標記）

一，Claude Code 決定載入哪份 project settings 的規則讀不到（harness 內部）。
只能反推「本 session 的 project 是 home、沒載 repo settings」，
**無法直接證明「從 repo 目錄啟動就一定會載入並觸發」。這一條仍然只有
owner 從 repo 目錄開 session 驗得到。**

二，「09-08 當時全域 settings.json 確實註冊過這三個 hook」沒有直接檔案
證據，現在全域已經沒有它們。時序判定是靠 hook 自述、`~/.forseti/` 遺留、
streak 三者一致反推。要坐實需要 settings.json 的版控或備份歷史。

三，全域 `~/.forseti/goal.json` 多出的 ISEEU 與 `/private/tmp` scope
是誰寫的，沒找到寫入者。`forseti-declare.mjs:27` 寫的是
`declarations.json` 不是 `goal.json`，hook 只讀不寫。寫者應該是
某個 CLI 或安裝腳本，還沒讀到那段，不猜。
